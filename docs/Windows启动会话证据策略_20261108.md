# Windows 启动会话证据策略（2026-11-08）

## 安全决策
Windows boot_identity() 继续返回 None。未证明每次内核启动唯一的标识不能授权旧启动进程死亡推断；不可用墙钟、boot_time、WMI LastBootUpTime、注册表时间或主机名替代。既有无启动证据档案不能自动升级为可信历史。

## 已核实资料与风险
- https://ntdoc.m417z.com/system_boot_environment_information ：phnt 定义包含 GUID BootIdentifier、FirmwareType、BootFlags。
- https://geoffchappell.com/studies/windows/km/ntoskrnl/inc/api/ntexapi/system_boot_environment_information.htm ：查询类为 0x5A (90)，GUID 位于0，Windows 8及以后大小32字节，更早为24字节；该接口未正式公开文档化。文中指出该标识来自加载器，BCDEDIT 使用它识别实际启动的已安装Windows系统。这不能证明它是每次启动唯一的会话标识。

结构布局可信不等于生命周期语义可信。相同会话连续读取稳定也不足以证明跨启动唯一；不能将 BootIdentifier 命名当作证明。休眠、快速启动、虚拟机恢复和系统克隆也需要单独界定。当前没有可靠依据证明该API可用于安全解锁，故不接入恢复判断。

## 验证边界
独立测试验证Windows始终拒绝生成启动证据，不调用未经验证的证据来源。Linux/mac分支保留。实机只读API探测仅记录状态、长度和同会话稳定性，不输出原始系统标识，不进行重启、不改变权限或安全设置、不触碰现有预览进程。

未来如接入经过证明的原生API：所有不支持、访问拒绝、异常、长度或布局不符、全零GUID必须返回None；明确版本化来源，不追溯补写旧档案。新增能力须附生命周期证据及隔离验证。

## 补充：KUSER_SHARED_DATA.BootId
Microsoft 官方结构文档：https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data 。其明确写明 BootId 是“Boot sequence, incremented for each boot attempt by the OS loader”。这是比 BootIdentifier 更相关的生命周期证据，但本次未找到有明确支持契约的用户态查询API；不采用硬编码共享页地址/跨版本字段偏移，不将32位计数器包装成UUID。尚未证明休眠/恢复及故障启动条件下的进程生命周期对应关系，因此本次不启用。

## 本机验证结果
使用项目 Anaconda 解释器运行独立测试：2 passed。原生 NtQuerySystemInformation 连续3次返回成功、32字节、非零且同会话一致的GUID；只读测试未打印原始GUID。此结果仅验证当前会话读取稳定，不证明跨重启唯一。独立测试只有两项：Windows不调用不可信来源且返回None，以及实机原生API同会话稳定性探测。未实现原生解析器，未覆盖候选值、错误或短返回的解析。Windows跨启动恢复仍是明确功能缺口，不应将安全跳过称为支持该功能。
